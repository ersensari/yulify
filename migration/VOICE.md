# Yulify voice migration to Pithagoras v0.2

Reference upstream: fbcbf31; Yulify baseline: 85fbe80. This is a migration map, not a deployed implementation. Keep the current worker and transport unchanged until a verified end-to-end replacement exists.

## Contract boundaries

* Upstream `packages/extension-api/server.d.ts` exposes `VoiceProvider`: synchronous state(), transcribe(one 16 kHz mono WAV), speak(one phrase, PCM/WAV at 24 kHz), and optional use(). It does not expose a realtime room, microphone tracks, voice tool/control events, or model/style prompt metadata. `extensions/voice-servers/src/server/provider.ts` implements only this simpler contract, without voice bearer authentication.
* Yulify `server/src/api/minicpm-duplex.ts` has a separate LiveKit room/worker bridge under `/api/sessions/:id/voice/qwen3/...`, session-bound tokens, single active room per portal, heartbeats, tool calls, transcript and interruption paths. `server/src/auth.ts` has a service key rule, and the bridge also verifies each per-room token. `server/src/server.ts` mounts a distinct bridge router: preserve both checks and route placement; extension `portal.router` alone mounts only under authenticated `/api/x/<package>/` and is not a drop-in replacement for worker URLs.
* Yulify `web/src/components/VoiceControl.tsx`, `VoiceStage.tsx`, `MiniVoiceBar.tsx`, `VoiceOrb.tsx`, `MiniCpmDuplexControl.tsx`, and `web/src/minicpm-duplex-room.ts` implement current full/mini views, levels, realtime controls and LiveKit. `VoiceControl` uses substantial chat state, composer integration, layout, events and Electron hooks. Upstream chat.overlay/chat.composer.above slots expose only ChatProps; embedding this control needs explicit shared host services or retaining an adapted core host component. Do not mount a second voice transport.
* Yulify `server/src/api/voice.ts` preserves saved `voice` config (including `breezeUrl` and `whisperUrl`), voice library and runtime-specific request mapping; `server/src/voice-auth.ts` supplies `VOICE_API_KEY`. Audio-cpp handles 24 kHz and 48 kHz PCM, engine-specific voices, instruction/style and 409 contention. v0.2 promises 24 kHz PCM; explicitly resample streaming 48 kHz or extend the contract and client; never relabel 48 kHz as 24 kHz. LiveKit uses its independent worker synthesis path.

## Integration sequence

1. Port existing server, DB settings/library, auth and full/mini frontend into the new layout with no format changes, and preserve current paths. Add small tested host interfaces for session tools, native voice rules, notifications, agent voices, bridge state and secure worker authentication; do not expose raw session internals or service credentials to web plugins.
2. Extract existing recognition and synthesis logic from Express handlers into callable server services shared by handlers and a `yulify-voice` provider. Adapt `state`, `transcribe`, `speak`, `use` without reimplementing engine payloads; handle 48/24 kHz contract mismatch. Register with `portal.voice.provide` without auto-changing an existing selection. Data migrations must be idempotent and preserve IDs, secrets, preset audio and configured service addresses, with rollback against a copy of each database.
3. Expose explicit client host hooks/slots for full + mini orb, audio levels, Electron/wake integration and room ownership. One chat owns one transport through switches between views; preserve mic release/interrupt/end behavior and the mini text input.
4. Move bridge implementation to the extension only when a supported worker ingress and per-room auth exist. Maintain old route compatibility while the workers are updated. Evolve both workers and local/homelab routes together, with no cross-portal session lookup.
5. Check migration with copied data, existing voice settings/presets, both Linux and Mac portal configurations, different keys and concurrent sessions. Check rejection of invalid service/room tokens and room cross-use, cancellation and 409 retry, 24/48 kHz output, style/voice selection, typed/muted turns and full/mini waveform levels. A synthetic LiveKit replay validates transport but cannot establish physical microphone, speaker or acoustic quality.

Do not substitute stock Pithagoras Voice/Voice Servers or claim the provider alone covers LiveKit, existing orb, saved voice data, per-agent voices or styled streaming. Do not restart production services for migration work.
